# 传输协议、双栈承载与 UDP 优先设计

> 设计约束（2026-11-01）：TCP/UDP 业务仅为 IPv4，HTTP(S) 入口支持双栈；Agent—服务器承载支持 IPv4/IPv6 自动选择，使用一个 QUIC/UDP 专用端口与一个 TCP/TLS 专用端口。Linux 客户端 TUN 只用于本地保源，隧道传业务载荷与可信来源元数据。双栈自动选路与按入口区分监听地址族已实现，具体参数及验收范围见 [实现记录](../reference/IMPLEMENTATION.md)，TUN 见 [Linux TUN 指南](../guides/LINUX-TUN.md)。本轮不调整中控设计；Windows TUN 不开发，公网 NAT、高丢包、大规模并发、长期稳定性和 frp 可比性能测试继续暂缓。

## 1. 设计目标

本项目学习 frp 的反向连接、工作流复用与资源管理模式，自行定义 Agent—边缘的协议、协商和调度，不以兼容 frp 线协议为目标。传输优先验证 QUIC/UDP，并提供 TCP/TLS 兜底和有界多承载并发。

frp v0.71.1 本身也支持 QUIC 等传输，选用 QUIC 并不是本项目独有的区别。本方案需要落实和验证的是独立线协议、双栈探测/回退、可靠流与数据报分工、共享端口 fanout 和账号约束下的多承载调度，不预先认定一定优于 frp。

这里改变的是 Agent 与边缘之间的承载。访问者继续使用普通 TCP、UDP 或 HTTP(S)；用户发布服务的公网端口、Agent 目标端口和隧道承载端口是不同资源。云控只下发连接计划，不进入业务数据热路径。

Agent 主动向服务器发起连接，每节点使用一个 UDP 专用端口和一个 TCP 专用端口，二者可使用相同数字。多个客户端、规则与业务流共享这对端口，通过承载复用和按流分发提高并发效率；不要求 Agent 开放入站端口，也不要求扫描范围端口或增加端口来叠加带宽。

传输类型与地址族是独立选择：IPv4 业务可由 IPv6 上的 QUIC 或 TLS 承载，HTTP 的 IPv6 访客身份也可经 IPv4 承载传递。IPv4 over IPv6 在本项目中是业务载荷层的传输安排，不增加原始 IP 包隧道、IPv6 TCP/UDP 业务或 IPv6 保源能力。

本文包含当前实现与后续目标，交付边界以 IMPLEMENTATION.md 为准。不宣称切换端口就能加速，也不承诺加密后流量不可识别。

## 2. 传输分层

~~~mermaid
flowchart TB
    Plan["云控：边缘端点、授权、能力与资源策略"] -.-> Session
    Session["Agent—服务器逻辑会话：设备与规则授权"] --> Primary["UDP 专用端口：QUIC，IPv4/IPv6"]
    Session --> Fallback["TCP 专用端口：TLS，IPv4/IPv6"]
    Primary --> Streams["可靠流：TCP、HTTP 请求、会话控制"]
    Primary --> Datagrams["数据报：UDP 业务载荷"]
    Fallback --> Mux["有界逻辑流复用与带长度报文帧"]
~~~

逻辑会话不等于一条物理连接。一个有效设备会话可以按云控计划连接多个边缘；每个 Agent—边缘组合可有多个已认证承载，但始终只使用自己的规则和账号预算。

### 2.1 QUIC 首选路径

使用标准 QUIC 和 TLS 1.3，自有应用协议在其上定义版本、能力、控制消息和业务绑定，不把自有隧道称作 HTTP/3。

- 普通 TCP 访问连接使用独立可靠流，HTTP 按请求建立独立元数据与流式消息上下文。
- UDP 应用报文优先使用协商成功的 QUIC DATAGRAM 能力，保留边界，不为丢失的数据报增加隧道层可靠重传。
- 授权、流创建/关闭、映射确认与预算相关通知使用可靠控制通道，不能依赖数据报顺序。
- 单个可靠流丢包不要求其他流等待该流补齐，但整个 QUIC 连接仍共享拥塞控制、连接级流控和底层链路。
- 数据报同样受拥塞控制和本项目资源调度约束，不作为绕过限速的旁路。

QUIC 的握手与流机制有机会改善建连耗时和丢包环境下的并发体验；实际收益取决于网络、包大小、CPU 和实现，不能把所有 UDP 环境都视为低延迟保证。

### 2.2 TCP/TLS 兜底路径

UDP 被阻断或不可用时，使用经服务器身份验证的 TCP/TLS 承载。TLS 内使用本项目自己的有界帧协议和逻辑流控制，参考成熟复用机制，但不直接发送 frp 登录消息或宣称 frp 线协议兼容。

TCP/HTTP 继续使用逻辑可靠流；UDP 报文若允许此兜底，则使用显式长度分帧。应用报文边界保留，但传输增加可靠有序交付等待：发生底层丢包时可能影响同一承载上的其他逻辑流。

实时 UDP 规则可以显式要求数据报承载，不满足时停止相应转发并报告。允许 TCP 兜底时，面板显示真实模式及延迟风险；客户端 TUN 的目标 TCP 由独立协议栈维护，隧道只转业务字节；TLS 复用仍有连接级队头阻塞。

协议回退不改变来源语义：TCP/UDP 严格保源仍需已验证的 Linux 客户端 TUN 或透明 socket 路径，不能回退到丢失来源的 socket 或 PROXY v2；HTTP 仍由 Agent 根据可信逐请求元数据构造回源头。

## 3. 专用接入端口、双栈与 fanout

### 3.1 资源与配置

每台服务器提供一个 QUIC/UDP 接入端口和一个 TLS/TCP 接入端口，可以绑定获准的 IPv4/IPv6 地址或通过域名发布 A/AAAA。Agent 只尝试已授权的候选地址与这对端口。多个候选地址不意味着多组端口，也不要求每个地址独占一个承载。

下表描述连接计划中的概念约束，沿用现有 endpoint、信任与预算机制，不在本轮增加中控 API 字段：

| 项目 | 含义 |
| --- | --- |
| 节点与候选地址 | 获准服务器的身份、IPv4/IPv6 字面量或域名；IPv6 host:port 使用方括号 |
| 两个专用端口 | 一个 QUIC/UDP 端口、一个 TLS/TCP 端口；各自可供双栈接入 |
| 服务器身份 | 原有 TLS server_name、证书与信任材料，连接任一候选地址均严格验证 |
| 承载能力 | 可靠流、数据报、报文大小及其他已验证能力 |
| 连接预算 | 每设备、每节点的承载总数、候选数量与并发拨号限制 |
| 运行状态 | 各监听地址族、候选地址及承载的实际可用/失败/排空状态 |

两个承载端口与用户业务端口池、共享 HTTP(S) 入口分别管理归属并统一检查占用。IPv4 TCP/UDP 业务、双栈 HTTP(S) 与双栈承载应分别控制绑定地址族，不能用一个全局双栈监听开关扩大四层业务范围。不同用途不能在同一监听元组上无条件共存；双栈通配监听的 IPv4 覆盖也需纳入冲突检查。

监听某个地址族失败时报告实际可用项与错误，不把全部地址标成已开放。承载端口或地址被移除后先停止新承载选择，再按排空或强制关闭策略处理旧承载；新端点未就绪时不静默转到任意端口。

### 3.2 fanout 与有界并发

fanout 指共享入口上的接入、解复用和分发：UDP 端口先按 QUIC 连接分流，TCP 端口接入 TLS 连接；认证后再按设备、规则、业务流及 UDP flow_id 路由到对应处理上下文。未知或未授权的流不创建目标连接，一个业务帧只交给它所属的流。

并发来自承载内独立流、少量有界承载与公平调度。接入握手、分发队列、流窗口、PPS 与内存都设上限，慢流不能阻塞整个共享分发循环。fanout 是数据面的职责约束，不预先指定必须采用内核 PACKET_FANOUT、SO_REUSEPORT 或某种线程模型，也不作未经实测的吞吐承诺。

每个服务器由一个精简转发进程管理自己的监听、承载和流状态，配置与授权从云控取得，不连接 MySQL/Redis。不同服务器的状态分别归属，不能因为使用相同信任体系就当成同一条可迁移的 QUIC 连接。

### 3.3 IPv4/IPv6 候选选择

服务器发布 IPv6 且 Agent 具备 IPv6 连通性时，可以优先尝试 IPv6。使用域名时将解析到的获准 A/AAAA 作为候选；字面量按自身地址族连接。IPv6 不存在、不可达或持续劣化时选择可用 IPv4，以握手结果和持续质量观测作判断，不假定 IPv6 一定更快。

同一传输类型内允许有界延迟竞速 IPv6/IPv4，避免不可达 IPv6 长时间阻塞 IPv4；QUIC 与 TLS 的启动/回退也受同一拨号预算约束。一条 IPv6 QUIC 路径失败时，仍可尝试 IPv4 QUIC，不能据此认定 UDP 整体不可用。QUIC 首选与 TCP 兜底原则继续保留。

候选的连接失败、退避与质量按实际远端地址和传输类型区分；一个地址族故障不应冷却另一个已知可用候选。以冷却和稳定窗口抑制频繁切换，选路主要作用于新流，不迁移或重放已建立业务。当前有界竞速时序、采样窗口和选路参数记录于 IMPLEMENTATION.md；这些是实现参数，不代表公网性能结论。

## 4. 自动探测与快速回退

连接计划支持 auto、quic_only、tls_only 等传输偏好。auto 优先验证 QUIC，同时为 TCP/TLS 设置有界的启动延迟或并行竞速，避免 UDP 黑洞导致用户等待很久。

~~~text
取得有效连接计划与短期授权
    ↓
从两个专用端口的获准 IPv4/IPv6 地址中挑选少量候选，优先探测 QUIC
    ↓
QUIC 及时就绪且能力满足 → 用于新业务
    ↓ 未及时就绪或网络不可用
启动/选用已认证 TCP/TLS → 明确报告回退原因
    ↓
后台按退避节奏复测 QUIC，恢复后优先承载新业务
~~~

- 超时、并行拨号数、候选数和重试频率有上限，IPv4/IPv6 竞速共用预算，空闲设备不持续扫描端口。
- 重复拨号、竞速失败的连接和预热备用连接都受节点承载预算约束，落败者关闭或作为有界备用。
- 以握手结果、RTT、排队、丢包/重传和数据报发送失败等本地信息评估路径；不能只看一次 ping。
- 使用冷却与稳定窗口避免来回切换，云控批量获取结果，不逐次参与选路。
- 凭据无效、会话过期、规则被撤销或服务器身份失败是授权/身份错误，不能通过换地址族、端口或降级成未认证连接绕过。
- 状态报告区分 UDP 无响应、QUIC 协商失败、数据报能力缺失、资源不足与 TLS/授权失败；超时只能说明当前路径不可用，不自动断言具体上游防火墙原因。

quic_only 在所有获准 QUIC 候选不可用时明确失败；tls_only 不做 UDP 探测。这两个模式都可以选择 IPv4/IPv6，传输偏好不等于地址族偏好。自动恢复的探测参数由实现原型确定，不在设计阶段写成未经验证的性能默认值。

## 5. 多承载调度

首阶段从少量承载开始，按待处理业务、队列与可用资源增减到云控批准的上限；不为每条业务连接建立一个新的公网承载端口。

新可靠流按承载可用窗口、排队、活动流和健康情况选择承载，建立后固定归属。按账号/规则公平调度与有界流控，不能将一条 TCP 字节流的片段随意分散到多个独立承载再假定天然有序。

UDP 按流绑定承载，避免逐包轮转制造额外乱序；需要改绑时使用可靠控制消息与新的流代次。数据报队列设置容量和期限，过期报文丢弃，不能在链路恢复后补发大量已经失去实时价值的数据。

多个 QUIC 连接拥有各自拥塞控制，仍受账号共享预算与边缘根限制。增加 Agent 数、IPv4/IPv6 候选或承载数不增加账号权重，不复制突发信用；握手、保活和额外封装开销计入节点实际资源。

QUIC 单连接的路径迁移、多个独立 QUIC 连接和 Multipath QUIC 是不同能力。首阶段不依赖 Multipath QUIC，也不承诺一条大流通过多个端口叠加带宽。

## 6. 逻辑会话与协议约束

### 6.1 版本与能力协商

采用项目独立的应用协议标识与 ALPN，协商协议版本、支持的传输能力、最大帧/报文、流窗口和数量限制。未知版本或不满足规则要求的能力返回结构化失败，不猜测兼容。

标准 TLS/QUIC 外层仍可被网络观察到。项目自有的应用标识、版本和帧定义用于协议演进、可靠传输与业务隔离，传输性能通过同等条件下的测试评估。

不自行设计密码算法。每条承载校验预期边缘身份，并通过现有设备密钥持有证明及云控短期授权绑定会话；加入已有逻辑会话也需完整认证，不能只知道会话 ID 就加入。

### 6.2 会话与流标识

至少区分：

| 层级 | 身份与用途 |
| --- | --- |
| 设备运行会话 | device_id + session_generation，云控决定有效代次 |
| Agent—边缘逻辑会话 | transport_session_id，关联该边缘的承载集合 |
| 物理承载 | carrier_id、传输类型、实际远端地址/地址族、端点和运行状态 |
| 业务流 | tenant/device/rule/version、flow_id、流代次与资源许可 |
| 数据帧/数据报 | 对应流、长度及必要的序号/分段字段 |

完整租户与规则身份可由已验证上下文索引，不必每包重复全部字段，但不能丢失绑定校验。来源元数据以及客户端 TUN 的本地回流五元组必须与获准流匹配，不能把 Agent 的隧道网络对端当成访问者来源。

TCP/UDP 流的 peer 只接受 IPv4 访客，目标解析也限定为获准 IPv4；HTTP 请求的来源元数据允许 IPv4/IPv6，并逐请求用于构造可信来源头。HTTP 回源走普通连接池，不绑定访客 socket 来源。业务族校验不能只依据承载的 IPv4/IPv6 地址。

流创建由可靠消息完成，接收端确认规则、会话、目标和资源准入后才接受该流数据报。未知 flow_id 的数据不能自行建立目标映射；暂存和等待确认也必须有界。

帧长度、活动流、流窗口、未确认控制请求、数据报队列和内存均有上限。关闭或取消及时释放关联资源，一个受限账号不能阻塞整个共享解复用循环。

首阶段不允许 0-RTT 执行授权变更、创建业务或发送目标业务数据，避免重放造成重复操作或额度占用；会话恢复也重新校验当前授权和规则版本。

## 7. 数据报大小、MTU 与分段

QUIC DATAGRAM 需双方协商，单帧还受路径 MTU 与 QUIC 包空间限制。协商接收上限不等于网络可以发送同样大小的 UDP 包，DATAGRAM 自身也不提供跨包分片重组。

对 UDP 应用报文使用有界隧道分段与重组；客户端本地 TUN 的 MTU 与 IP 分片独立处理；不依赖外层 IP 分片在互联网稳定可用，也不静默截断报文。

隧道分段需要消息标识、总长度、片段信息和流代次；单包大小、片段数、重组时间和每账号缓存均有上限，缺片到期丢弃。它与业务侧 IP 分片及 ACL 的分片检查是不同层次，不能相互替代。

QUIC 初始报文的最低 UDP 载荷要求不代表单个 DATAGRAM 可直接发送同样大的载荷。IPv4/IPv6 外层路径的 MTU 由所选承载处理，客户端 TUN 仍仅处理目标侧 IPv4；不增加原始 IPv6 包、扩展头或 ICMP 的业务转发。

## 8. 故障、迁移与已有业务

### 8.1 新流与既有可靠流

首选承载失败后，新流可以选择仍可用的 QUIC 承载或获准的 TCP/TLS 兜底。已经绑定到失效承载的普通 TCP/HTTP 流，首阶段按失败结束，不宣称在另一个承载上无损续传。

未实现应用级确认、偏移和去重前，不能在重连后盲目重放 TCP 字节或 HTTP 请求，尤其不能重复目标写入。HTTP 错误行为沿用站点代理设计，响应已开始时不能重新生成另一张错误页。

一个承载失败只影响其相关业务，不能关闭同设备所有其他承载或同节点其他账号。状态同时展示会话部分可用与受影响规则，避免把“有备用连接”显示成所有旧业务无损。

### 8.2 UDP 改绑（后续目标）

UDP 报文流若映射和授权仍有效，可以原型验证在可靠改绑确认后继续使用同一业务身份，经新的承载转发；更改流代次并拒绝旧代次迟到报文，序号窗口允许合理乱序并限制重放。

改绑不续满账号额度、不创建第二份会话许可，也不重建成其他 Agent 的目标。规则、目标和来源元组保持一致才可能继续；映射已丢失、租约失效或目标改变时必须停止并重新准入。

客户端 TUN 不改变已有 TCP 隧道流的失败语义，不在新承载重放目标业务。切换可能丢失在途 UDP 包，面板保留事件与丢包统计。

### 8.3 QUIC 路径变化

NAT 重绑定或网络地址变化使用 QUIC 规范支持且所选库实际实现的路径验证能力。不能把切换到另一进程、另一服务器、另一地址族或任意新端口都称为同连接迁移；条件不满足时建立新的已认证承载，并执行前述业务故障或改绑语义。

## 9. 与 ACL、限速及节点容量的关系

访问者来源 ACL 继续在边缘按原始公网五元组执行，Agent 目标限制继续判断最终目标。用户 TCP/UDP ACL 不作用于云控连接或 Agent—边缘承载入口；承载的身份准入与节点防护由独立配置管理。

所有传输类型、IPv4/IPv6 候选和多个承载共同消费同一账号预算。基准、峰值、突发信用、周期额度和并发许可不因路径回退、重连或改绑重置。活动业务流与物理承载分别计数，UDP 数据报不能绕过 PPS、队列和内存限制。

业务净载荷与物理字节继续分别计量；QUIC/TCP 底层重传不重复计算同一业务帧；客户端 TUN 的 IP 头、ACK 和目标侧 TCP 重传也不计应用用量。隧道分段只计一份原始业务载荷，外层额外头、探测及重传进入物理统计。

应用流调度必须发生在写入共享承载之前。必要时分离可靠流和数据报的承载，降低大流对交互业务的影响；分离策略仍在节点总容量和账号公平预算内验证。

## 10. 云控与前端展示

沿用既有中控连接计划、身份与预算机制，服务器使用两个专用端口及获准候选地址，Agent 在有效计划内本地选择地址族与承载，不通过高频请求云控获取每次拨号许可。本轮不增加中控业务流程或数据表。

观测目标包括实际远端地址/地址族、传输类型、活动承载、逻辑流数、握手耗时、RTT、可用的 QUIC 包统计与候选失败原因。已有报告能表达的部分继续复用，缺少字段的部分作为后续契约核对项，不在文档中当作已发布接口。来源、单位、采样区间和统计截至时间明确。

用户界面的目标是分别展示业务入口地址族、实际承载地址族与 QUIC/TLS 状态；管理员查看两个专用端口及各地址族监听结果。保源要求、数据报要求与网络模式分别表达，不把 IPv6 HTTP 入口或 IPv6 承载显示成 IPv6 TCP/UDP 保源能力。

前端页面和 release 嵌入见 [前端与二进制嵌入设计](frontend-and-embed-design.md)，账号调度与计量见 [连接复用与资源控制设计](multiplexing-and-resource-control-design.md)。

## 11. 实现顺序与后续验收

在既有协议、认证、QUIC/TLS 回退与 IPv4 客户端 TUN 的基础上，先落实业务地址族边界和两个专用端口，再补充双栈 HTTP 与双栈承载自动选路验证。动态 UDP 改绑保持后续目标，不因使用了 QUIC 库就认定已有流可无损切换。

以下列出设计验收条件；已有 IPv4 证据见 IMPLEMENTATION.md，新增双栈条件尚未验收：

1. 验证项目协议版本/ALPN、服务器身份、会话加入与旧授权拒绝，不依赖 frp 线协议。
2. 分别经 QUIC/IPv4、QUIC/IPv6、TLS/IPv4、TLS/IPv6 承载运行 IPv4 TCP/UDP，检查 socket 与 Linux TUN 模式的目标来源和载荷。
3. IPv6 不存在、无路由或黑洞时，IPv4 候选在有界时间内可用；IPv6 QUIC 失败但 IPv4 QUIC 可用时仍保留 UDP 首选，UDP 整体不可用时 TCP 兜底。
4. 双栈 HTTP(S) 入口可回源 IPv4 目标，正确编码真实 IPv6 来源头；覆盖伪造头、多访客复用、流式响应及 WebSocket。
5. TCP/UDP 在 socket/native 两种模式均不接纳 IPv6 访客或 IPv6 目标；仅有 AAAA 的目标明确失败，HTTP 和承载的双栈监听不扩大四层业务范围。
6. 两个专用端口支持多客户端、规则和流的有界 fanout，设备/规则隔离、未知 flow 拒绝、慢流隔离和共享预算保持有效；不扩展为大规模并发压测。
7. 验证普通和大 UDP 报文、空报文及隧道分段在两种外层地址族下保持边界；不要求通用 ICMP/PMTU 业务转发。
8. 验证双栈通配监听占用冲突、部分地址族监听失败、端点排空及节点重启，业务端口和承载端口不混用。
9. 数据报能力缺失、授权到期、ACL 收紧和 TUN 关闭时不静默降低来源要求；换地址族不绕过服务器身份认证。
10. 选路与观测包含有界候选、退避和稳定窗口，故障只影响相关承载；既有 TCP/HTTP 流不重放，UDP 改绑不作为本轮完成条件。

公网 NAT、高丢包、大规模并发、长期稳定性和 frp 可比性能测试继续暂缓；多端口叠加与通用组网不作为本轮目标。

## 12. 机制依据

- [RFC 9000：QUIC](https://www.rfc-editor.org/rfc/rfc9000)：可靠流、流控、路径验证、迁移与 UDP 载荷要求。
- [RFC 9001：QUIC 的 TLS](https://www.rfc-editor.org/rfc/rfc9001)：TLS 1.3 与 QUIC 的安全握手。
- [RFC 9002：丢失检测与拥塞控制](https://www.rfc-editor.org/rfc/rfc9002)：多个流共享连接级拥塞控制。
- [RFC 9221：QUIC DATAGRAM](https://www.rfc-editor.org/rfc/rfc9221)：不可靠报文、能力协商、帧大小和拥塞约束。
- [frp v0.71.1 客户端传输配置](https://github.com/fatedier/frp/blob/v0.71.1/pkg/config/v1/client.go)：Protocol 已包括 tcp、kcp、quic、websocket 和 wss，不能把 QUIC 本身描述为 frp 缺失的能力。
- [既有 frp 复用研究](multiplexing-and-resource-control-design.md)：区分承载复用与 HTTP CONNECT 公网入口，不直接推导线协议兼容。
