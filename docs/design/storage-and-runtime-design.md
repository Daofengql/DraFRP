# 三个二进制、云控存储与内存回退设计

## 1. 部署基线

系统交付三个独立二进制：云控服务端、边缘服务端和客户端（Agent）。当前按单实例设计：云控不做多副本集群，每个边缘和客户端也是独立进程；仍可向云控注册多台边缘和多台客户端。

只有云控连接 MySQL 和可选 Redis。边缘与客户端不包含业务数据库、Redis 客户端或完整管理前端，不承担用户、套餐、配额账本和 ACL 模板等业务管理。

| 二进制 | 职责 | 本地状态与外部依赖 |
| --- | --- | --- |
| 云控服务端 | 前端/API、身份与权限、资源配置、配额分配、用量账本、模板管理、状态汇总 | MySQL 必需；Redis 可选，不可用时用自管理进程内存库 |
| 边缘服务端（Linux） | IPv4 TCP/UDP 与双栈 HTTP(S) 接入、两个专用端口的双栈承载认证和分发、局部限额执行与上报；不使用 TUN | 必需的节点身份/启动配置，以及内存中的规则、连接、流映射、计数和预算余额 |
| 客户端 Agent | 设备绑定、主动选择 IPv4/IPv6 承载、IPv4 TCP/UDP 目标访问、HTTP 回源、可选 Linux 本地 TUN 保源 | 持久设备凭据/本地设置，以及内存中的运行配置、连接和流映射 |

单实例约束不取消云控处理并发请求时的数据库事务、唯一约束和版本校验。当前不引入多云控协调、分布式锁、选主或 Redis 消息总线。

本文描述目标设计，已实现范围见 [实现与验收记录](../reference/IMPLEMENTATION.md)。2026-11-01 仅同步客户端/服务器网络职责，中控存储、缓存、授权与预算机制保持既有设计；不创建数据库、安装服务或生成实际连接配置。

## 2. 存储分工

### 2.1 MySQL：云控的持久业务数据

MySQL 是业务配置、授权与账本的权威来源，主要持久化：

| 数据 | 内容 |
| --- | --- |
| 用户与空间 | 用户、资源归属、权限、停用状态 |
| 设备与边缘 | 身份公钥、凭据/撤销信息、设备会话代次、边缘运行代次及节点注册 |
| 绑定与浏览器会话 | 一次性绑定请求的有效期/消费结果，登录会话摘要、有效期与撤销状态 |
| 规则与策略 | TCP/UDP 规则、HTTP(S) 站点、管理员自行创建的 ACL 模板及发布版本 |
| 入口资源 | 业务端口/域名占用、承载端点池、待回收状态 |
| 域名与证书 | 归属、证书元信息及需要保存的加密材料 |
| 配置版本 | 设备/边缘期望 revision、应用确认及其观测时间 |
| 配额与用量 | 账号策略、周期、已发预算、未结清预留、幂等用量汇总和结算进度 |
| 审计 | 重要业务操作与配置变更记录 |

浏览器会话与一次性绑定的正确性不依赖 Redis；缓存丢失后可从 MySQL 校验或恢复。设备和边缘凭据仍按各自身份隔离，不通过共享缓存获得其他设备权限。

高频数据先在各运行进程中累计，再按批次上报/汇总。MySQL 不逐包记录转发，也不让云控逐连接代替边缘完成数据面检查。

### 2.2 Redis：可选临时存储

Redis 可加速热点查询、有限期运行状态、会话查询结果及短期汇总展示；其数据应可从 MySQL 或后续节点上报重建。采用统一临时存储接口，使调用方不依赖 Redis 命令或数据结构。

Redis 不保存唯一一份账号余额、端口占用、设备会话代次或撤销结果。Redis 清空、过期、故障或被停用，不代表额度归零重发、端口已释放或旧授权重新有效。

### 2.3 自管理内存库：Redis 的可替换实现

未配置 Redis、管理员停用 Redis、启动时无法连接或运行中 Redis 不可用时，云控自动使用自己的进程内存库。它是临时键值存储实现，不是 MySQL 的内存替代品，也不要求管理员部署第二个数据库进程。

内存库至少具备并发安全读写、TTL、单键原子更新、条目/字节上限、过期清理、容量淘汰和命中/淘汰指标。只实现本项目需要的接口，不模拟完整 Redis 服务或对外开放 Redis 端口。

容量达到上限时优先清理过期与可重建缓存，限制单键大小，并合并同一缓存键的回源查询。不得为了“可用”而丢弃持久账本或忽略授权检查；缓存写入失败按缓存未命中/不可缓存处理，业务正确性仍依赖 MySQL。

## 3. 云控内部边界

~~~mermaid
flowchart TB
    Browser["浏览器控制台"] --> Cloud["单实例云控：API 与业务服务"]
    Cloud --> MySQL["MySQL：持久配置、授权、配额账本"]
    Cloud --> Store["统一临时存储接口"]
    Store --> Redis["Redis：可选"]
    Store --> Memory["自管理内存库：默认或故障回退"]
    Cloud --> Bus["进程内事件与配置同步"]
    Bus -. 规则、授权、预算 .-> Edge["边缘：精简转发与本地执行"]
    Bus -. 设备配置与连接计划 .-> Agent["客户端 Agent"]
    Edge <-->|已授权承载| Agent
~~~

业务持久化接口与临时存储接口分开，禁止在 Redis 错误时把 MySQL 的业务写入改写到内存。配置变更以 MySQL 提交为准，再失效缓存并唤醒同步任务。

配置通知和浏览器 SSE 使用云控进程内事件机制，不需要 Redis Pub/Sub。通知是触发器，设备/边缘仍按期望版本重新同步；云控重启后从 MySQL 恢复待同步差异，重连时发送完整快照，丢失一次内存通知不等于丢失配置。

## 4. Redis 故障与恢复

### 4.1 后端选择

- Redis 未启用：直接进入 memory 模式，属于正常支持的部署方式。
- Redis 已启用且健康：使用 redis 模式。
- Redis 连接失败或操作超时：有界等待后切换到 memory，记录原因；不要求用户确认，也不阻止正常云控启动。
- 后台按退避和抖动探测，稳定恢复后切回 redis；不能让每个业务请求都重新拨号探测。

MySQL 健康而 Redis 不可用时，云控仍可就绪；管理状态页显示实际临时存储后端及降级原因。切换和恢复期间需要处理的并发请求有界，不无限排队等 Redis 恢复。

### 4.2 数据切换语义

Redis 与内存都按临时缓存处理，切换不要求将全部键双写、复制或合并。每次云控启动、缓存后端切换使用新的缓存命名空间/代次，恢复 Redis 时从空逻辑命名空间按需重建，避免读到故障前遗留的旧值；不清空管理员 Redis 中其他应用的数据。

临时缓存键统一设置有限 TTL，旧命名空间通过到期回收；恢复探测有稳定窗口，避免频繁切换产生持续缓存重建和无界遗留。

MySQL 事务成功后，即使 Redis 失效操作失败，业务写入也已成立。云控使对应缓存不可再读或切换缓存代次，不能返回旧结果当作本次已应用状态，也不能把缓存错误当成数据库事务回滚。

缓存填充与失效需有代次/版本检查，防止旧查询在写入失效后又把旧值填回。身份撤销、会话替换、端口分配和新预算签发等关键决策核验持久状态，不仅依赖缓存命中。

本进程 API 限流等需要保持连续的短期计数由独立内存状态维护，不因缓存后端切换重新发满一份额度；账号业务用量和预算始终以 MySQL 已发放/已结算状态为准。

## 5. 重启与故障边界

### 5.1 云控重启

进程内缓存、订阅者和即时在线视图允许丢失。启动后从 MySQL 恢复配置、资源占用、授权代次、会话、配额周期和未结清预算，再等待节点重连与上报。

旧的“最后在线/已应用”记录保留观测时间，新进程尚未收到心跳时显示等待确认，不直接视为当前在线。内存为空不代表没有活动授权、没有额度消耗或入口可以重新分配。

重连沿用或替换设备会话遵循原有代次与租约规则。速率/并发份额在确认回收或失效前仍被占用；周期字节信用即使租约到期，未结清部分也继续保守占用或计入已用，不能自动退还。云控重启不重新发满预算，也不重置周期累计用量。

### 5.2 MySQL 不可用

MySQL 是必需依赖。启动时不可用则云控不就绪；运行中不可用时停止需要持久确认的配置修改、绑定、授权签发/续期、预算发放和资源回收。不能把数据库故障伪装成 memory 模式后继续业务写入。

边缘与客户端按已有有效授权、配置和本地剩余预算继续，期限或预算到达边界后停止相应业务。缓存可以辅助说明最后观测状态，但不能被用来扩大旧授权或确认新的持久结果。

## 6. 精简边缘的职责

业务决策统一由云控完成：用户归属、套餐选择、全局额度计算、端口分配、规则版本、模板发布及审计持久化均不放到边缘。

边缘只执行云控已批准的结果：

- 维护自己的控制连接及短期规则/授权快照。
- 通过一个 UDP 与一个 TCP 专用端口认证 IPv4/IPv6 客户端承载，按设备/规则/流定位 Agent，转发 IPv4 TCP/UDP 和双栈入口的 HTTP(S)。
- 执行下发的来源 ACL、局部计数/令牌、并发上限和租约期限，不处理模板业务或自行计算账号套餐。
- 管理转发必需的普通连接、UDP 流映射、TLS 与系统错误页；服务器不维护 TUN、DNAT 或保源策略路由，相关本地回流状态仅属于 Linux 客户端。
- 累计实际转发计数，批量上报状态与用量，不维护 MySQL 账本或 Redis 缓存。

这些内存状态属于转发执行，不是独立业务系统。把它们完全移到云控会使逐包/逐流转发依赖控制面，与云控不承载业务及低频批量统计的目标冲突。

首阶段边缘不增加本地业务数据库或持久用量日志。边缘崩溃可能丢失尚未上报的计数；云控按未结清预留保守处理，避免额度重发。若以后要求崩溃后也精确恢复实际用量，需要另行设计，不能假定 Redis 能恢复边缘未上报的数据。

边缘每次进程启动取得新的运行代次，预算绑定该代次；本地状态已经丢失的旧 grant 不得在新进程重新初始化余额、计量序号或突发信用。云控先登记并处理旧代次未结清预留，再从可分配余额发放新预算，不要求边缘新增数据库来恢复旧余额。

客户端仅访问自己的目标和流，持久设备凭据与必要本地设置，不保存云控业务数据库。边缘和客户端重启后重新认证/同步，不因残留文件自行恢复已撤销业务。

## 7. 构建与配置归属

建议命名为 drafrp-cloud、drafrp-edge、drafrp-client，实际目标名可在创建工程时统一；交付数量固定为三个独立二进制。

Go 工程若按当前假设实现，可分别设置三个 cmd 入口。云控引用业务存储、临时存储和管理前端包；边缘/客户端只引用所需的协议、身份与数据面包，不通过公共初始化代码被迫连接 MySQL/Redis。

release 构建仅在云控目标嵌入 React/MUI 产物。边缘只带必要的轻量 HTTP 系统错误页，客户端不携带管理台。MySQL/Redis 连接参数只属于云控配置，不下发到边缘、客户端或浏览器。

云控配置分别提供 MySQL 连接池/超时、Redis 启用与连接参数、内存库容量/TTL/清理参数。此处只定义配置职责，不生成真实地址、口令或部署文件。数据库结构迁移由云控启动流程或维护子命令管理，不新增第四个常驻服务二进制。

## 8. 后续验收

以下为目标检查清单，已完成项以 IMPLEMENTATION.md 为准，本轮不调整或重测中控存储机制：

1. 仅部署 MySQL、不配置 Redis，云控与三个角色的完整流程可运行。
2. Redis 启动不可达、运行超时、反复波动及恢复时，自动回退/重建缓存，接口等待有界。
3. 缓存切换、清空和云控重启不重发预算、不释放占用端口、不复活旧会话或旧权限。
4. 验证缓存填充与失效竞争、一次性绑定消费、登录撤销、配置版本与幂等用量写入。
5. 内存库达到容量上限、TTL 到期和并发访问时，资源有界且可回源到 MySQL。
6. MySQL 故障时不把持久写入切入内存，节点仅在既有授权/预算内继续。
7. 边缘与客户端在没有 MySQL/Redis 配置和网络权限时仍能按其角色运行，构建不携带完整管理前端。
8. 边缘崩溃、云控重启和未结清用量场景下，额度预留与统计新鲜度得到如实展示。
