# 内网穿透服务设计记录

> 2026-11-01 设计约束：服务器端固定 Linux；TCP/UDP 仅转发 IPv4，HTTP(S) 保留 IPv4/IPv6 入口；客户端与服务器之间的承载可使用 IPv4/IPv6，UDP 优先、TCP 兜底。TUN 仅属于 Linux 客户端，HTTP 来源使用逐请求可信头。本文定义目标行为，新增约束与当前实现的差异见 [实现记录](../reference/IMPLEMENTATION.md)。本轮不调整中控的身份、存储、授权和配额设计。

## 1. 当前产品定位

这是一个“中心云控 + 公网边缘节点 + 客户端 Agent”的集中式内网穿透服务，交付云控服务端、边缘服务端和客户端三个独立二进制。

当前按单实例设计：云控不做多副本集群，每个边缘和客户端独立运行；仍支持注册多台边缘、多台 Agent。只有云控使用 MySQL 与可选 Redis，Redis 不可用时自动使用云控自管理的进程内存库。

当前确认的产品范围：

- 用户通过云控面板管理设备、边缘节点、转发规则和 HTTP(S) 站点。
- 第一阶段支持 IPv4 TCP、IPv4 UDP 和双栈入口的 HTTP(S) 三类穿透；HTTP 与 HTTPS 属于同一类站点代理能力。
- 一个用户可以绑定多个 Agent；每台 Agent 有独立身份、凭据、会话和配置。
- 访问者通过公网端口或域名访问服务，无需安装访问者侧客户端。
- 云控负责认证、授权、配置和状态，边缘节点承载业务流量。
- Agent 部署在目标服务器或能够访问目标服务的服务器上。
- 用户无需维护 frpc/frps 配置文件；Agent 可以持久化设备凭据。
- Linux Agent 可以选择启用客户端本地 TUN，通过本地协议栈绑定访客 IPv4/端口访问目标；关闭时采用普通 socket 转发。隧道传输业务载荷与来源元数据。
- TCP/UDP 需要透明保源的规则，以目标应用通过 socket 直接识别真实公网源 IP、源端口为要求；不向业务流插入 PROXY Protocol v2 头。
- HTTP(S) 通过可信 HTTP 转发头传递访客来源：边缘将观测到的源 IP 等信息放入隧道请求元数据，Agent 构造回源请求并写入类似 X-Forwarded-For 的头；不依赖 TUN 原生保源。
- TUN 的可用性与透明保源能力分别检测。权限、路由或协议条件不足时明确报错，不悄悄降低规则要求。
- 参考 frp 的承载连接复用机制；按账号分配共享额度，同时执行边缘性能配置的节点总上限。
- 账号带宽允许统计周期内波动，以基准速率、突发信用和可配置峰值描述；边缘本地执行，云控批量统计与协调。
- TCP/UDP 支持分层来源 ACL、连接状态管理和管理员模板；只设计模板机制，具体条目及默认模板由管理员后续添加，不内置策略内容。HTTP(S) 不接入这套 ACL。
- 管理前端采用 React + TypeScript + Material UI；release 使用 Go 的 go:embed 将静态产物嵌入云控二进制，开发使用 Vite 热更新；实际交付范围以 IMPLEMENTATION.md 为准。
- Agent—边缘使用独立协议，每节点提供一个 QUIC/UDP 专用端口和一个 TCP/TLS 专用端口，通过共享入口的 fanout 与有界多承载复用服务多设备、多规则和多流；UDP 优先、TCP 兜底，承载地址族可自动选择 IPv4/IPv6。
- 云控保存业务配置、身份与配额账本，边缘是精简转发器，只执行下发规则和限额；边缘/客户端不连接 MySQL 或 Redis，完整管理前端只嵌入云控。

本文保留产品设计基线；TCP/UDP 保源与 HTTP(S) 来源头传递的当前数据路径、平台限制和验收见 [来源信息传递与 TUN 设计](transparent-source-design.md)。

连接复用、账号额度、限速/限流和节点容量的具体方案见 [连接复用与资源控制设计](multiplexing-and-resource-control-design.md)。

TCP/UDP 来源策略、管理员默认模板、目标边界及状态撤销见 [TCP/UDP ACL、模板与防火墙设计](tcp-udp-acl-firewall-design.md)。

控制台页面、交互与 release 构建见 [前端与二进制嵌入设计](frontend-and-embed-design.md)；UDP 优先、专用端口、双栈选路与回退语义见 [传输协议与承载设计](transport-protocol-design.md)。

三个二进制、单实例职责及 MySQL/可选 Redis/内存回退见 [运行与存储设计](storage-and-runtime-design.md)。

### 1.1 地址族与来源传递约束

| 区段或模式 | 地址族 | 来源语义 |
| --- | --- | --- |
| 访客 → 服务器 TCP/UDP 业务入口 | 仅 IPv4 | 从实际 socket 获取访客 IPv4/端口，普通模式与保源模式均遵守此范围 |
| 访客 → 服务器 HTTP(S) 入口 | IPv4/IPv6 | 反向代理按请求记录真实访客地址，经可信元数据传给 Agent |
| 服务器 ↔ Agent 承载 | IPv4/IPv6 | QUIC/UDP 优先、TLS/TCP 兜底；外层地址族独立于业务与来源地址族 |
| Agent → TCP/UDP 目标 | 仅 IPv4 | socket 模式使用 Agent 地址；Linux TUN 模式绑定访客 IPv4/端口 |
| Agent → HTTP(S) 目标 | 继续满足单栈 IPv4 回源 | 普通 HTTP(S) 连接与连接池，逐请求设置可信来源头；IPv6 回源不作为本轮新增要求 |

IPv6 访客可以通过 HTTP(S) 反代访问 IPv4 内网站点，目标从来源头获取真实 IPv6 地址。TCP/UDP 的 IPv6 业务入口、IPv6 目标与 IPv6 原生保源不在本轮设计范围，也不引入 NAT64 或映射地址来声称原样保源。

IPv4 over IPv6 在本项目中指经 IPv6 上的 QUIC/TLS 承载传输 IPv4 业务载荷和来源元数据。客户端 TUN 的包只在客户端与目标之间投递；本项目不提供通用 IP 隧道、默认路由或设备组网。

服务器提供 IPv6 地址且 Agent 具备 IPv6 连通性时，可优先尝试 IPv6，并结合有界连接探测及持续质量观测选择承载；IPv6 不可用或持续劣化时可选择 IPv4。地址族选择与 UDP/TCP 回退分别处理，不把 IPv6 存在视为一定更快。

## 2. 系统角色

### 2.1 云控中心（Control Plane）

云控负责：

- 用户、租户、设备和边缘节点管理。
- URL 登录、设备绑定、设备凭据轮换和撤销。
- TCP/UDP 转发规则与 HTTP(S) 站点的持久化。
- 域名归属、证书绑定、回源 Host 和 HTTPS 回源参数管理。
- 计算每台 Agent 可用的规则、边缘节点和连接计划。
- 签发限定设备、边缘、规则版本和有效期的短期准入凭证。
- 配置同步、应用状态、操作审计和资源配额。
- 账号配额策略、跨边缘预算租约、周期用量账本与边缘容量配置。
- 周期汇总边缘批量上报的用量与需求，不对每个包或业务流进行同步限速决策。
- 管理 TCP/UDP ACL 模板、默认绑定和强制策略，发布版本化快照并汇总实际应用状态；模板内容由管理员维护。
- 同源提供用户/管理员控制台、API 和状态事件，发布产物携带对应版本的前端静态资源。
- 下发边缘传输入口池、允许的传输能力与有界连接计划，批量汇总实际选路和降级结果。
- 使用 MySQL 持久保存配置、身份、资源占用、配额预留和幂等用量账本；Redis 仅为可选临时存储，不可用时自动切换到自管理内存库。

云控默认不承载业务转发流量。HTTP(S) 系统错误页由边缘节点提供，不依赖实时访问云控。

### 2.2 边缘节点（Edge Node / Relay）

边缘节点负责：

- 提供 IPv4 TCP/UDP 公网入口及 IPv4/IPv6 共享 HTTP/HTTPS 入口，分别应用监听地址族约束。
- 执行云控批准的监听、域名路由和设备绑定，并在 TCP/UDP 路径执行来源 ACL 与连接状态检查。
- 处理公网 HTTPS 证书与 TLS 终止。
- 为每个 HTTP 请求生成可信来源元数据，并经授权隧道交给 Agent。
- 将 TCP 字节、UDP 载荷或 HTTP 请求及可信来源元数据送往正确的 Agent。
- 对 Agent、设备会话和规则版本进行准入校验。
- 在 Agent 离线、隧道不可用或回源失败时返回 HTTP(S) 系统错误页。
- 上报节点、规则、隧道和连接状态。
- 在复用承载和各协议路径执行账号限速、请求/并发限制、流量额度及节点总资源上限。
- 提供与用户业务入口分开管理的一个 QUIC/UDP 端口和一个 TCP/TLS 端口，支持双栈接入、认证承载及按设备/规则/流分发，并执行共享预算。

边缘是独立的精简转发二进制，不管理用户、套餐、业务账本或 ACL 模板，不连接 MySQL/Redis。它只保留转发必需的内存状态，机械执行云控下发的规则、局部预算和期限，再批量报告结果；预算分配与持久结算由云控完成。

边缘节点有独立的节点身份，不能使用用户或 Agent 的凭据登录云控。边缘只使用普通监听，不创建 TUN、DNAT、访客地址池或保源策略路由；保源本身不要求边缘具备网络管理权限。

可参考 frp 的承载复用和流控机制；访客身份通过认证元数据交给客户端，本地 TUN 保源不要求服务器转发原始 IP 包。

### 2.3 受控端 Agent

Agent 负责：

- 首次通过 URL 绑定到用户选定的租户或个人空间。
- 保存独立设备凭据，启动后自动认证。
- 仅获取属于自己的规则和连接计划。
- 按需主动连接被授权的边缘节点。
- 向服务器两个专用接入端口主动出站，在获准地址中执行 IPv4/IPv6 选择、QUIC 优先、TCP/TLS 回退和受限多承载调度。
- 应用配置，访问目标服务，上报状态和错误。
- 按隧道中的可信请求元数据构造 HTTP(S) 回源请求，设置转发头、Host 和回源 TLS 参数，再将目标响应返回边缘。
- 按本地设置启用普通 socket 或 Linux 客户端 TUN 网络模式，报告真实运行能力；已有 Linux transparent 路径按独立能力保留，Windows 不提供保源模式。
- 在 TUN 模式下维护所需接口、受限路由、流量映射和回包路径。
- 在 TCP/UDP 转发前校验最终目标与本地允许范围，只处理属于已授权规则和活动流的数据。

云控配置不能越过 Agent 本地对网络管理权限和 TUN 的授权。用户修改网络模式后，云控应重新评估受影响的规则。

客户端是第三个独立二进制，不携带完整管理前端，也不连接 MySQL/Redis；本地只持久化设备凭据和必要设置，业务配置按云控授权同步。

## 3. 多 Agent、设备绑定与凭据

### 3.1 资源归属与隔离

统一以 tenant_id 表示资源归属；个人用户也有自己的个人空间。用户是操作主体，设备是独立的运行主体。

关系如下：

~~~text
用户 → 有权管理的个人空间或租户
租户 → 多台 Agent
租户 → 多条规则 / HTTP(S) 站点
每条规则 → 一台确定的 Agent + 一个确定的边缘节点
一台 Agent → 多条规则 → 按需连接多个边缘节点
一个边缘节点 → 多个租户下的多台 Agent
~~~

第一阶段每条规则只有一个目标 Agent，不包含多个 Agent 之间的负载均衡和自动故障转移。目标 Agent 离线时，不能自动把流量送到同账号下的另一台设备。

例如：

~~~text
用户 alice
  device-home：家庭服务器
    TCP 规则：edge-001:20022 → 127.0.0.1:22
  device-office：办公室服务器
    HTTP(S) 站点：app.example.com → 127.0.0.1:8080
~~~

device-home 不能获取 device-office 的规则、边缘准入凭证、设备凭据或目标服务访问权。两台设备出现相同的本地地址 127.0.0.1 不构成共享目标。

控制面 API 和边缘准入均校验资源归属，不能仅根据客户端提交的 device_id、rule_id 或 tenant_id 放行。租户级配额还需限制设备数、规则数、端口数和并发资源。

账号资源额度以 quota_subject_id 聚合。同账号的多台设备、多条规则和多个边缘共同消费该账号预算，不为每台 Agent 复制一份完整额度。团队可绑定显式的团队配额主体；归属与额度主体映射由云控产生。

### 3.2 首次绑定

每台 Agent 独立完成一次绑定：

~~~text
本地生成设备密钥
    ↓
向云控申请短时、一次性的绑定请求，关联设备公钥
    ↓
展示登录 URL / 绑定码
    ↓
用户在浏览器登录，确认目标空间和设备信息
    ↓
Agent 凭设备端绑定凭据领取绑定结果
    ↓
持久化 device_id 和设备私钥或可轮换的设备凭据
    ↓
后续自动认证，领取短期访问凭证
~~~

浏览器登录会话不下发给 Agent。登录 URL 不承担长期设备凭据的作用；同账号的多台设备也不共用一个长期 Token。

云控地址可通过内置默认值或启动参数指定，仍无需用户编写业务转发配置文件。

### 3.3 凭据与运行会话

区分以下材料：

- 设备身份：长期持久化，支持单独轮换和撤销。
- 云控访问凭证：短期有效，仅用于该设备的控制面操作。
- 边缘准入凭证：短期有效，仅用于指定边缘和批准的规则。
- 运行会话：session_id 与单调递增的 session_generation，用于识别重连和过期实例。

同一 device_id 默认只有一个有效控制会话，但该会话可连接多个边缘节点，也可建立多个业务连接。复制凭据启动第二个实例应报告身份冲突，不应无条件反复互踢；复制安装实例应重新绑定为新设备。

重连可在有效期内恢复原会话。需要替换会话时，由云控原子地递增代次并禁止旧代次续租。新代次在相关边缘确认旧代次失效，或旧租约到期后取得转发权，避免网络分区时出现两个有效实例。

撤销一台设备只撤销该设备的会话、凭据和规则转发权，不影响同账号的其他设备。租户级停用则影响其全部设备。

## 4. 三类穿透模型

### 4.1 TCP

~~~text
IPv4 访问者 → 边缘 IPv4 TCP 端口 → IPv4/IPv6 承载 → 指定 Agent → IPv4 TCP 目标
~~~

规则指定边缘、监听端口、目标 Agent 和 IPv4 目标地址。普通 socket 模式直接连接目标；TUN 模式将可信访客 IPv4/端口绑定到客户端本地协议栈，建立独立目标连接。两种模式的隧道均传业务字节，TCP 两端分别握手、确认和重传；不插入业务前缀，不要求复刻公网 TCP 序列号或选项。

### 4.2 UDP

~~~text
IPv4 访问者 → 边缘 IPv4 UDP 端口 → IPv4/IPv6 承载 → 指定 Agent → IPv4 UDP 目标
~~~

保留报文边界，维护每个来源与目标的双向映射，并定义空闲超时、报文大小和资源上限。不同来源或不同规则的响应不能混发。

UDP 的实现不能直接复用 TCP 字节流复制逻辑。透明模式下也需处理 MTU、分片、回包和映射过期。

### 4.3 HTTP(S)

HTTP(S) 是域名驱动的双栈站点代理：边缘负责 IPv4/IPv6 公网入口、TLS、域名路由和系统错误页，Agent 负责构造回源 HTTP 请求、设置来源头并访问目标服务。IPv6 访客可访问单栈 IPv4 目标；来源头与公网及回源连接的地址族分别处理。

~~~text
IPv4/IPv6 浏览器 https://app.example.com
    ↓
边缘：匹配域名、处理证书、终止公网 TLS，记录访客 IP
    ↓
通过隧道传送请求及可信的逐请求来源元数据
    ↓
Agent：设置 XFF 等转发头，按站点配置构造回源请求
    ↓
http://127.0.0.1:8080 或 HTTPS 目标
~~~

云控配置：

- 入口域名及对应边缘节点。
- 公网证书及证书来源，例如上传或托管签发。
- 目标 Agent、目标服务地址和回源 HTTP/HTTPS 协议。
- 回源 Host：保留入口 Host 或显式覆盖。
- HTTPS 回源的 SNI、证书校验策略与信任材料。
- 代理超时及系统错误页。

入口域名与回源 Host 是不同配置。公网 TLS 由边缘处理，HTTPS 回源连接由 Agent 发起；默认校验回源证书，按规则使用 SNI 和信任材料。

每个隧道请求携带 request_id、规则 ID/版本、设备会话、源 IP/端口、入口 scheme 和经校验的 Host，并绑定到对应请求流。Agent 仅从已认证边缘的隧道元数据获取来源信息，不能信任公网用户自行填写的来源头。

默认由 Agent 重建 X-Forwarded-For、X-Real-IP、X-Forwarded-Proto、X-Forwarded-Host 等头。边缘和 Agent 清除或覆盖来访的同名头、Forwarded 及其他受管来源头，不直接拼接未经信任的 XFF。XFF 中写入 IP，不把源端口拼入其 IP 值；确需源端口时使用单独约定的头。具体头集合与编码见来源信息传递设计。

来源头属于逐请求信息，不存成回源连接属性。不同访客可以复用同一站点的回源连接；每次请求独立写入来源头，连接池仍按租户、规则版本、目标和 TLS 配置隔离。

目标的 socket 对端仍是 Agent；应用通过 HTTP 头获取真实访客信息。需要按目标框架的方式将 Agent 配为可信代理，不要求目标解析 PROXY v2 或启用 TUN。

HTTP(S) 可以共用边缘的 80/443，无需为每个站点分配一个公网业务端口。第一阶段按精确域名路由，一个入口域名绑定一条活动站点规则，不自动分流到其他 Agent。

错误行为：

| 情况 | 边缘响应 |
| --- | --- |
| Agent 离线、隧道未就绪 | 503 系统错误页 |
| 目标连接失败或回源 TLS 失败 | 502 系统错误页 |
| 回源超时 | 504 系统错误页 |
| 域名未匹配 | 默认 404，不进入其他租户的站点 |

边缘保留本地错误页。HTTPS 错误页以 DNS 和公网证书正常为前提；公网 TLS 握手本身失败时无法返回 HTTP 页面。

Agent 将连接失败、TLS 失败和超时以结构化结果交给边缘。目标正常返回的 HTTP 响应，包括其自身的 4xx/5xx，继续代理给访问者；系统错误页只处理代理链路故障。若响应已开始发送后链路才中断，只能按协议结束失败流，不能追改成新的错误页。

### 4.4 Agent 网络模式与规则要求

TCP/UDP 网络模式由设备选择，规则声明所需能力，二者共同决定能否运行：

| Agent 状态 | 不要求原生保源的 TCP/UDP 规则 | 要求真实源 IP/端口的 TCP/UDP 规则 |
| --- | --- | --- |
| socket 模式 | 可运行；目标通常看到 Agent 地址 | 不满足能力要求 |
| TUN 已启用，保源数据路径通过检查 | 可运行 | 在已验证的平台和协议范围内可运行 |
| TUN 已启用，但权限或回程路由不满足 | 按独立 socket 能力判断 | 不得标记就绪 |

TUN 接口存在不等于保源能力已就绪。TCP/UDP 的 native 要求同时保留访客 IPv4 和源端口；不能仅保留 IP 却显示成功。关闭 TUN 后，普通 socket 规则直接连接目标；已有严格 native 规则若不再满足能力则停止并报告，切回普通转发应显式改选 socket。

HTTP(S) 使用独立的应用层回源能力，socket 或 TUN 模式均可运行；关闭 TUN 不应停用 HTTP(S) 规则。HTTP 来源头与 TCP/UDP 的 socket 原生源地址是不同能力，按协议类型分别校验。

不默认启用 PROXY Protocol v2。隧道内部仍需封装与鉴权；TCP/UDP 不额外插入业务协议前缀，HTTP(S) 由 Agent 将来源元数据转换为正常 HTTP 头。

## 5. 规则与资源模型

### 5.1 公共字段

~~~text
rule_id
tenant_id
device_id
edge_id
protocol: tcp | udp | http | https
enabled
rule_version
target
required_capabilities
source_mode: socket | native | forwarded_headers
quota_subject_id: derived-by-control-plane
created_at
updated_at
~~~

每条规则只引用同一租户下的设备和可授权使用的边缘。设备可以管理自己的运行状态，不能自行修改 target、监听端口、域名或规则归属。上表仅表达规则概念，实际字段以 [API 合约](../reference/API-CONTRACT.md) 与共享模型为准，本轮不增加中控字段。

### 5.2 协议字段

| 类型 | 主要配置 |
| --- | --- |
| TCP | 受控监听地址、公网端口、目标地址、连接超时、原生保源要求、来源 ACL/模板引用、目标访问范围 |
| UDP | 受控监听地址、公网端口、目标地址、会话空闲超时、原生保源要求、来源 ACL/模板引用、目标访问范围 |
| HTTP(S) | 入口域名、证书绑定、回源协议、Host、SNI、超时、可信来源头策略 |

TCP/UDP 沿用当前 `source_mode: socket/native`：socket 为普通转发，native 同时要求真实访客 IPv4 和源端口。HTTP(S) 使用 `forwarded_headers`，由 Agent 将逐请求来源元数据转换为可信回源头，不要求 native 能力。

TCP/UDP 独立保存来源策略/模板引用、目标访问限制和管理员默认选择的来源；HTTP(S) 不保存这套 ACL 绑定。默认模板是新规则的默认选择，强制上级策略是不可放宽的约束，两者分开。模板管理仅提供机制，不预填实际 IP、地区集合或允许/拒绝条目。

规则可选的带宽、请求或并发限制只能收紧父级策略。账号策略和边缘容量独立下发并版本化，不能在每次规则更新或设备重连时重置账号用量。

TCP/UDP 使用边缘固定的 IPv4 监听地址，通过业务端口池分配资源。目标为 IPv4 字面量或可解析到获准 IPv4 的域名；域名仅有 AAAA 时报告无可用 IPv4 目标，不转为 IPv6 或地址转换。数据库约束同一 edge_id、传输协议和公网端口不能重复；TCP 与 UDP 可以使用相同端口号。HTTP 的 80/443 需与 TCP 端口池协调保留。

用户业务端口池、共享 HTTP(S) 入口与 Agent—边缘两个专用承载端口分别管理并统一校验监听占用；承载端口可以使用同一数字的 UDP 与 TCP。多个 IPv4/IPv6 候选地址仍对应同一对承载端口。IPv4 TCP/UDP 业务监听不能因 HTTP 或承载启用双栈而一并接受 IPv6 业务。同一监听元组的共享需要独立分流设计。

自定义域名先验证归属；平台分配的域名由平台管理。域名统一规范化并占用，防止不同租户重复绑定。证书私钥仅分发到承担该入口的边缘，不下发给 Agent。

删除规则后，监听端口或域名占用须等边缘确认关闭旧规则，或对应授权租约失效后才能释放，不能在节点离线时立即分配给另一个设备。

### 5.3 运行状态

配置与状态分开存储，至少包括：

~~~text
desired_rule_version
agent_applied_version
edge_applied_version
device_session_generation
agent_config_revision
edge_config_revision
state: pending | applying | ready | degraded | disabled | error
last_error_code
last_error_message
last_seen_at
~~~

设备和边缘的快照 revision 各自单调递增，不能用各条规则 version 的最大值代替快照版本。

TCP/UDP 另行展示期望与已应用的 effective_policy_revision、模板发布版本及可选地址库版本。收到配置不等于已生效；策略收紧后的旧状态清理或可靠阻断也属于应用确认条件。

设备在线、隧道在线、规则配置已应用、目标服务健康分别展示。配置已应用不代表应用服务一定健康；TCP/UDP 可采用按需检查，HTTP(S) 可结合请求结果和可选健康检查。

## 6. 动态配置与规则生命周期

~~~text
用户提交规则
    ↓
云控校验权限、资源占用和设备能力，事务保存期望配置
    ↓
生成新的规则版本及受影响设备/边缘的快照 revision
    ↓
通知相关 Agent 和边缘重新同步
    ↓
两端校验并幂等应用，分别上报结果
    ↓
云控根据配置版本、授权、隧道及能力状态汇总就绪情况
~~~

长连接通知只是同步触发，云控保存的期望状态为准。断线重连后拉取完整快照，清除已删除或已转移的规则，避免丢失一条增量通知就永久不一致。

每台 Agent 只接收自己的业务目标配置。每个边缘仅接收自己负责的监听、路由、设备映射和鉴权材料。

规则变更使用预期版本进行并发校验。回滚生成新版本，不降低版本号。旧版本配置、旧设备会话和过期授权不得重新激活监听或数据流。

规则从 device-A 转移到 device-B 时：

1. 校验 B 的归属、能力和目标配置，生成新版本。
2. 边缘停止向 A 分配新业务，关闭第一阶段约定需要终止的旧连接/UDP 映射。
3. 清理 A 的授权；在 B 就绪且边缘确认新映射后，开放新版本业务。
4. 任一步失败都显示切换未完成，不能随机选择 A 或 B。

第一阶段停用、删除、设备转移、目标地址变更和权限收紧会终止相关旧业务。其他更新是否支持连接排空需按实现验证，不承诺全部无损热更新。

关闭 TUN 前展示受影响的 TCP/UDP 保源规则；模式改变后立即重新评估能力，停止不再满足要求的规则并报告原因。HTTP(S) 的来源头能力独立于 TUN，继续运行。

## 7. 连接计划与边缘准入

### 7.1 连接布局

- 每台 Agent 主动维护自己的云控控制连接，承载配置同步、心跳和状态。
- 每个边缘维护独立的云控控制连接。
- Agent 仅在有已启用且获准的规则时连接对应边缘，不连接全部节点。
- 同一 Agent 与同一边缘之间复用数据承载或连接池，业务流按规则和会话隔离。
- 一个 Agent—边缘逻辑会话可向同一对专用端口建立少量承载，在获准 IPv4/IPv6 地址中选择；本轮不要求范围端口扫描或多端口叠加。
- 控制同步、TCP/HTTP 业务流、UDP 载荷的逻辑通道分离。优先使用 QUIC 可靠流及 DATAGRAM，UDP 不可用时选择经认证的 TCP/TLS 兜底；能力不足不静默放宽规则要求。
- HTTP 请求的来源元数据绑定到单个请求流，HTTP 多路复用时也不得作为整条承载连接共享的状态。
- 参考 frp transport.tcpMux 的复用与流控思路，自行定义版本化协议和业务绑定；物理承载、活动业务流和 HTTP 请求分别计数并受资源限制。frp 的 tcpmux HTTP CONNECT 入口作为另一项机制单独评估。

示例：A 的规则全部在 edge-1，B 的规则分别在 edge-1 和 edge-2，则 A 只连 edge-1，B 连接 edge-1 和 edge-2。它们不共用设备凭据，也不互相转发。

连接计划继续沿用既有设备身份、会话代次、配置 revision、允许的边缘及 endpoint、TLS 服务名/信任信息、传输偏好、承载能力/数量上限和对应规则集合；目标布局是每边缘一对专用端口及其 IPv4/IPv6 候选地址。本轮不重设计中控接口。短期边缘凭证独立续期，不作为永久配置保存。

新业务按可用承载与预算选择路径，既有 TCP/HTTP 流首阶段不承诺跨失效承载无损续传；UDP 改绑仍为后续目标。切换承载地址族不改变 IPv4 访客身份，也不能复制账号额度。具体协商、快速回退与 MTU 边界见 [传输详细方案](transport-protocol-design.md)。

### 7.2 双向认证与授权

Agent 验证边缘服务器身份，边缘验证云控签发的短期准入凭证，并验证连接方持有凭证绑定的设备密钥。

边缘凭证至少绑定：

~~~text
issuer / audience(edge_id)
tenant_id
device_id
session_generation
device_key_thumbprint
rule_grants:
  - rule_id
    rule_version
    allowed_actions
    protocol / required_capabilities
issued_at / expires_at
token_id
~~~

凭证授予的是云控已批准规则的执行权，不允许 Agent 自行创建监听、替换目标设备、扩大端口范围或访问其他规则。边缘以自己的已同步配置核对监听端口、域名、协议、规则版本和设备映射。

准入还需通过对应账号和节点的资源检查。quota_subject_id、配额策略和可消费预算来自云控签发的策略或预算租约，不信任 Agent 自报的套餐、余额或限制值。

每个逻辑业务流或报文通道关联 tenant_id、device_id、session_generation、rule_id、rule_version 和 flow_id；这些信息由认证上下文与云控配置共同校验，不能仅信任数据包中的自报字段。

客户端 TUN 对应的业务流同样执行规则级校验，只向本地协议栈和 TUN 投递匹配已批准 IPv4 流量的数据。启用 TUN 不等于允许任意目的地址、任意源地址或设备之间互访。

### 7.3 访问者权限

Agent 的边缘准入与公网访问者权限分别配置。本节 ACL 仅面向 TCP/UDP，HTTP(S) 不增加来源 ACL、地区模板或应用访问控制设计。

TCP/UDP 来源策略在本轮数据面匹配 IPv4/CIDR、来源端口、协议，以及具备对应能力时的地区集合；规则的公网入口端口用于确定规则。通用地址库或既有 ACL 格式的 IPv6 解析能力不扩大业务范围，也不作用于双栈 HTTP 或承载入口。管理员后续自行创建模板并配置默认选择；本轮不改变中控模板模型，不内置实际策略内容。

所有适用的强制策略与规则策略均需允许，子级不能覆盖上级拒绝；同一策略按明确顺序首次匹配，并要求显式默认动作。边缘本地判断，不逐流请求云控。默认模板的替换权限和强制策略分别管理。

匹配使用边缘普通监听观察到的访客五元组完成来源判断；Agent 另行校验最终目标。策略收紧要停止不再允许的 TCP 连接、UDP 映射及客户端 TUN/内核流，不仅检查新连接。

地区能力使用管理员配置的版本化本地地址库，范围与未知结果动作由管理员定义。模板更新、地址库更新和临时条目到期都需重新判断受影响状态；批量统计不会延迟已经收到的策略生效。

宿主机过滤只管理本项目的对象，按平台报告实际执行能力。策略语义、模板生命周期与诊断见 [详细方案](tcp-udp-acl-firewall-design.md)。目标应用自身认证仍按原有机制工作。

### 7.4 离线、续期与撤销

短期授权采用有截止时间的租约，并提前续期。令牌过期不只阻止新登录，还要限制已建立会话继续创建业务和转发数据。

云控暂时不可用时，已有规则只在有效租约内继续；到期停止相应转发。在线撤销通过推送尽快生效，节点失联时最大撤销延迟受剩余租期和允许的时钟误差限制。

边缘关闭授权时清理普通监听、业务连接与 UDP 流；客户端同步清理对应 TUN 流及回流规则，避免旧状态在下一次重连后复活。

Agent 断线采用退避和抖动重连。是否持久化最近有效配置另行决定；只保存身份的基线下，Agent 重启需要联系云控重新获取配置，不承诺离线重启恢复。

## 8. 第一阶段边界与实现顺序

第一阶段包含：

- 同账号多 Agent，独立绑定、配置、准入、撤销和重连。
- IPv4 TCP/UDP 规则与 IPv4/IPv6 入口的 HTTP(S) 站点。
- HTTP(S) 域名、证书、回源 Host、Agent 注入的可信来源头和边缘系统错误页。
- Agent 可选 TUN；透明保源按平台与协议验证结果开放。
- 承载连接复用、账号共享的限速/限流/流量额度，以及边缘性能配置的总上限。
- TCP/UDP ACL 模板管理、默认绑定、分层来源判断、目标边界和状态撤销；不附带具体策略，内核过滤及地区能力按验证结果开放。
- React + Material UI 控制台与 release 前端嵌入；用户和管理员共用应用，按服务端权限操作。
- 独立传输协议、每节点一个 UDP 和一个 TCP 专用承载端口、QUIC 首选与 TCP/TLS 兜底，IPv4/IPv6 自动选路及有界并发按实际验证结果开放。
- 三个独立二进制、单实例云控、MySQL 持久存储和可选 Redis；Redis 不可用时云控自动使用自管理内存库，边缘/客户端不承担数据库业务。

第一阶段不包含：

- STCP、SUDP、XTCP、访问者侧 Agent、打洞直连、设备间组网或通用 VPN。
- IPv6 TCP/UDP 业务入口、IPv6 TCP/UDP 目标、IPv6 原生保源和跨地址族的四层保源转换。
- 同一规则的多 Agent 负载均衡与自动故障转移。
- 用户手工维护 frpc/frps 配置。
- 未验证的平台或网络部署下，宣称 TCP/UDP 无条件保留真实源 IP 与端口。
- HTTP(S) 通过原生 socket 保留访客源 IP/端口；当前采用逐请求可信头传递。
- 未经验证的 Multipath QUIC、任意单流多端口叠加带宽或跨承载无损续传承诺。

分别验证 IPv4 TCP/UDP 在 socket/TUN 模式下经 IPv4/IPv6 承载转发，以及双栈 HTTP 入口到 IPv4 目标的可信来源头、连接池隔离与错误行为。IPv6 HTTP 和承载自动选路仍需新增验收，不能引用既有 IPv4 记录作为证据。公网 NAT、高丢包、大规模并发、长期稳定性和 frp 可比性能测试继续暂缓。

资源控制先验证单边缘的账号共享限制与节点根限制，再验证跨边缘预算。跨边缘全局额度在预算共享实现前不能标记为已支持。

## 9. 术语约定

- 云控中心：Control Plane，单实例业务控制面，唯一连接 MySQL/可选 Redis 并携带完整管理前端的二进制。
- 服务器端 / 边缘节点：Edge Node / Relay，固定 Linux 的独立精简转发二进制，承载公网入口和下发策略的本地执行，不使用 TUN。
- 客户端 Agent / 设备：第三个独立二进制的服务提供端实例；同账号可以有多个，不连接业务数据库。
- 访问者：访问公网端口或域名的一方，不要求安装客户端。
- 规则：绑定一个边缘和一个目标 Agent 的 TCP、UDP 或 HTTP(S) 配置。
- 连接计划：云控为某一 Agent 计算的边缘端点、规则与承载安排。
- 原生保源：IPv4 TCP/UDP 目标应用通过 socket 获取服务器观察到的访客 IP/端口，无需解析 PROXY 头；不表示复刻公网 TCP 连接的全部协议状态。
- HTTP 来源头传递：边缘观测访客身份，经隧道逐请求传递给 Agent，再由 Agent 设置回源 HTTP 头；不改变目标 socket 的对端地址。
- TUN：仅供 Linux Agent 在本地协议栈与目标内核之间读写 IPv4 包的可选接口，不作为隧道的业务线协议。
- 承载复用：多个逻辑业务流共享少量 Agent–边缘传输连接；与 HTTP CONNECT 公网入口复用分开。
- 配额主体：云控计算的账号或团队额度归属，同一主体的所有设备共享额度。
- 承载端点：服务器一个 UDP 专用端口和一个 TCP 专用端口及其 IPv4/IPv6 候选地址，与访问者使用的业务公网端口池分开。
- fanout：共享接入端口上的承载解复用和按设备、规则、流的并发分发，队列与资源有界。

## 11. 连接复用、账号额度与边缘上限

参考 frp v0.71.1 已核对的两种机制：transport.tcpMux 通过 yamux 在底层连接上创建多个逻辑流；type=tcpmux 使用 HTTP CONNECT Host 复用公网入口。优先参考前者构建承载，后者是否开放须考虑访问者的 CONNECT 兼容性，不能无感替代所有普通 TCP 入口。

资源限制分开定义：

| 限制 | 账号维度 | 边缘维度 |
| --- | --- | --- |
| 传输速率 | 所有设备/规则共享上下行基准、峰值护栏与突发信用 | 全部账号共享节点处理预算与物理出站整形 |
| 接入速率 | 新连接/秒、HTTP 请求/秒 | 节点总建连、TLS 和请求处理能力 |
| 并发 | 活动 TCP、HTTP 请求和 UDP 会话 | 总活动流、承载数、文件描述符和内存 |
| 累计用量 | 账号在指定周期的共享字节额度 | 权威计量、有限信用与用量上报 |

账号标称 100 Mbps 表示基准速率，允许按策略短时达到 120 Mbps 等更高速率。例如 100 Mbps 持续补充、50 MB 突发信用和 120 Mbps 峰值护栏，满桶时可在节点容量允许的情况下以 120 Mbps 传输约 20 秒，信用耗尽后回到基准。统计窗口只观察波动，不自动重置突发信用；若需要严格窗口总字节限额，作为额外策略显式配置。

执行原则：

- 限制由边缘执行，Agent 可选地进一步收紧，但不能绕过或放宽账号策略。
- 账号管理员配置子规则限制，平台管理员配置账号策略和边缘容量；不同权限不能混用。
- 在每个边缘先做账号本地共享，再用云控分配的短期预算保证跨边缘的基准补充速率、突发信用和峰值份额不被复制。
- 节点根限制始终约束所有账号。账号有剩余额度不代表当前节点一定提供该速率，也不构成保底承诺。
- 多路复用前按账号公平调度，限制排队、窗口和内存；不能让一个账号的限速阻塞整个复用读循环。
- 控制通道保留少量处理预算；账号令牌、已消费用量和并发许可不因重连、续期或规则更新而重置。
- 细粒度计量和令牌扣减在边缘本地执行；云控按可配置周期合并统计与调整预算，例如先验证 30 秒批量上报，不逐包或逐流请求云控。
- 统计窗口、上报周期、预算再分配周期和租期分别配置。带宽允许波动不自动放宽周期累计流量、并发数或节点容量。
- 业务数据量与物理网卡流量分别计量。入站接纳上限不能宣称为对已到达外部链路流量的硬限制。

跨边缘预算、计量口径、协议执行点和验收条件见 [详细方案](multiplexing-and-resource-control-design.md)。

## 12. 前端与发布

控制台以设备、TCP/UDP 隧道、HTTP(S) 站点和账号用量组织用户页面，管理员另有节点、端口池、配额、空 ACL 模板管理与审计。设备在线、隧道可用、配置应用和目标健康分别显示，不将保存成功等同于转发就绪。

前端采用 React + TypeScript + Material UI，Vite 构建静态产物。当前按 Go go:embed 设计 release 嵌入，开发通过独立 Vite 服务热更新；发布运行不依赖 Node 或外部前端目录。基础路径、SPA fallback、API 路由与缓存一并定义，具体见 [前端方案](frontend-and-embed-design.md)。

## 13. 三个二进制与云控存储

云控服务端负责全部业务管理与持久状态，MySQL 为必需依赖；Redis 可选，未配置或故障时使用进程内自管理内存库，恢复后重建缓存。MySQL 不可用不能改为内存持久化，也不能重发已有预算或释放仍占用的资源。

边缘服务端只保留网络转发及下发策略执行，客户端只负责设备连接和目标访问，两者均不连接 MySQL/Redis。三个目标分别构建，管理前端仅进入云控；具体职责、回退与重启语义见 [运行与存储设计](storage-and-runtime-design.md)。
