# 2026-11-06 Linux Performance Report

## Environment and method

Measurements ran in the dedicated Hyper-V Ubuntu VM: Linux 6.8.0-138, AMD Ryzen 9 7940HX, 8 vCPU, 8 GiB RAM, Go 1.26.10. Go benchmarks used one logical CPU, one-second samples, and five repetitions. CPU profiles used the maximum UDP packet parser benchmark for five seconds. Race tests were run separately from timing measurements.

The initial profile attributed 99.48% cumulative CPU time to `sumBytes` while parsing a maximum-size UDP packet. Address validation and packet construction were below 1% combined. The TUN packet-view preparation path was already around 6-7 ns/op with zero allocations, so it was left unchanged.

## Change and results

`sumBytes` now reads 8-byte chunks with `binary.BigEndian.Uint64`, adds their four 16-bit lanes, and handles 4-byte, 2-byte, and odd-byte tails. This preserves the one's-complement word sum while reducing loop and load overhead. A reference 16-bit implementation checks representative lengths, odd tails, maximum packet length, and several seeds.

| Benchmark | Reference median | Optimized median | Change |
| --- | ---: | ---: | ---: |
| Checksum, MTU payload (1480 B) | 472.1 ns/op | 217.6 ns/op | -53.9% |
| Checksum, maximum UDP payload (65515 B) | 20.159 us/op | 8.807 us/op | -56.3% |
| Full parse, small TCP packet | 111.4 ns/op | 72.0 ns/op | -35.3% |
| Full parse, 1500 B TCP packet | 541.4 ns/op | 272.4 ns/op | -49.7% |
| Full parse, maximum UDP packet | 21.354 us/op | 9.381 us/op | -56.1% |

Checksum comparisons used five samples per version in the same benchmark suite. The full-parse figures compare a three-sample baseline with five post-change samples and are supporting measurements; the direct checksum comparison is the controlled result. All variants reported zero allocations. The post-change maximum-packet profile still centers on `sumBytes` because checksum work is the benchmark's measured operation; `binary.BigEndian.Uint64` accounts for about 3.8% flat CPU, down from about 23% for 16-bit loads.

## Verification and limits

Passed `go test -race ./internal/tun` in the VM and `go test ./internal/tun` on Windows. The package includes a reference-sum equivalence check through the maximum packet size plus existing parser, rewrite, and malformed-packet tests.

These package microbenchmarks measure only the single-threaded TUN packet hot path. The separate socket loopback results below do not establish TUN or WAN throughput, production capacity, or comparative performance.

## End-to-end socket forwarding on VM loopback

### Setup and behavior

The dedicated Hyper-V Ubuntu VM used Linux 6.8.0-138, AMD Ryzen 9 7940HX, 8 vCPU, 8 GiB RAM, and Go 1.26.10. Release cloud/edge/client binaries ran `scripts/smoke.py --performance` with separate fresh MySQL databases for QUIC-only and TLS-only. A Python TCP/UDP echo target ran on the same VM. Each mode used 200 persistent TCP RTT samples, 4 MiB TCP payloads at 1/4/16 concurrent flows, and UDP payloads of 128 B/1400 B/48000 B with windows 1/16/64 (500 packets for the first two sizes; 100 for 48000 B). Process CPU/RSS was sampled every 200 ms.

Both transport smoke runs passed the 512 KiB TCP transfer, 48 KB/empty UDP cases, active-flow revocation, and embedded-console check. The first QUIC run stalled during the concurrent transfer workload. Source inspection found that unlimited traffic grants were not marked waitable at the credit boundary even though the cloud extends the same lease during sync. Unlimited grants now set `wait_for_credit`; `TestMySQLUnmeteredGrantWaitsForCreditRenewal` verifies that a low-credit lease keeps its ID and is extended. The MySQL regression test and both full smoke modes passed after the fix.
